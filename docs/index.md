# Custom Project

## Dataset

My Kafka producer uses a modified sales dataset containing individual
sales transaction records. Each record represents a sale and includes
fields such as sale_id, customer_id, product_id, quantity, unit_price,
payment_method, timestamp, and total sale amount. I modified the
original sales dataset by replacing the region_id field with
payment_method to better analyze how customers pay for purchases.

## Kafka Messages

The producer reads records from the sales dataset and sends each
record as a JSON message through Kafka. The Kafka topic used for
this project was `streaming-06-scenarios-fuemmeler`. Each message
contains the sales transaction fields from the dataset, including
the modified payment_method field. The messages are keyed using
the sale identifier to help maintain message organization
and traceability.

## Consumer Processing

The consumer subscribes to the Kafka topic and receives each
sales transaction message. For this project, the consumer processes
six messages as configured in the .env file. The consumer validates
incoming records, logs message details, and stores valid and rejected
records in DuckDB. The consumer also processes the payment_method
field and uses it for storage summaries and analysis. In addition,
the consumer updates a custom visualization that displays streaming
sales information as messages are consumed.

## Experiments

For Phase 4, I customized the .env file by creating a project-specific
Kafka topic, reducing the producer message count to six messages,
and increasing the message interval to four seconds. These changes
allowed me to more easily observe message production and consumption.

For Phase 5, I enhanced the DuckDB storage functionality by
modifying the summary query to group records by payment_method.
I added SQL aggregation functions including COUNT(), SUM(), and
AVG() to calculate transaction counts, total sales, and average sale
amounts for each payment method. I also updated the logging output
to display these business metrics.

## Results

The producer successfully sent sales messages to the custom Kafka
topic, and the consumer successfully received, validated, and stored
the records in DuckDB. The modified payment_method field appeared
correctly in the consumed messages and database records. The DuckDB
queries generated useful summaries showing transaction counts, total
sales, and average sales by payment method. The custom visualization
updated as messages were consumed, providing a live view of the
streaming data.

## Interpretation

This project demonstrated how streaming data moves from a producer
through Kafka to a consumer where it can be validated, analyzed,
visualized, and stored for future use. Compared to the original
example, I customized the dataset, changed the tracked field from
region_id to payment_method, modified the environment configuration,
enhanced the visualization, and expanded the DuckDB analytics.
Watching messages move through Kafka helped me understand how
real-time data pipelines operate and how organizations can monitor
transactions as they occur. The stream provided business intelligence
by identifying sales activity by payment method and calculating
key metrics such as transaction counts, total sales, and average
sales, which could help businesses understand customer purchasing
behavior and payment preferences.
